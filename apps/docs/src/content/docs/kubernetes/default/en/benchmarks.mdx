# Benchmarks

FerrisKey 0.10.1 and Keycloak 26.8.1 were run through the same load scale on the same Kubernetes cluster, with the same resources, the same PostgreSQL setup and the same 1,000 users, on six endpoints: `client_credentials`, `password`, `refresh`, `introspect`, `userinfo` and `jwks`. Measured by Nathaël Bonnal; the full report with every step is in [IAM-performance-tester](https://github.com/ferriskey/IAM-performance-tester/blob/main/reports/2026-10-31-ferriskey-vs-keycloak.md).

:::callout{variant="info" title="Build measured"}
FerrisKey is built from `main` at `ace8c1a`, the same code as the `v0.10.1` tag (the two differ only in documentation). It runs with `REFRESH_TOKEN_FORMAT=opaque` and `REFRESH_TOKEN_COMMIT=async`, two settings introduced in 0.10.1 that are off by default; see [refresh](#refresh) for what they change.
:::

## Summary

- FerrisKey sustains the same highest step as Keycloak on all six endpoints.
- It uses less CPU than Keycloak almost everywhere, often half as much at the same rate. The one exception is `userinfo` from 3,200 req/s up.
- On `refresh`, at 800 req/s, FerrisKey's p95 is 5.7 ms against 14.5 ms, with 40 % less CPU.
- Keycloak keeps a lower tail latency (p99) on `client_credentials` from 800 req/s, on `password`, and on `introspect` and `userinfo` from 3,200 req/s.
- The gap is widest on the machine-to-machine endpoints (`client_credentials`, `refresh`, `introspect`, `jwks`); the human `password` login is where Keycloak keeps the lower tail.
- FerrisKey uses less memory: 618 MiB at most, against 823 MiB for Keycloak.

## Sustained rate, latency and CPU

The sustained rate is the highest step with under 1 % errors, at least 95 % of the target rate served, and a p95 under 250 ms. Latency and CPU are read at 800 req/s, except for `password` (80 req/s), where Argon2id hashing makes each request expensive by design. CPU is that of the IAM server alone, in cores, averaged over the measured minute.

| Endpoint | FerrisKey sustained | Keycloak sustained | FerrisKey p95 | Keycloak p95 | FerrisKey CPU | Keycloak CPU |
|---|---|---|---|---|---|---|
| `client_credentials` | 3,200 req/s | 3,200 req/s | 2.7 ms | 2.0 ms | 0.66 cores | 0.94 cores |
| `password` (80 req/s) | 160 req/s (highest step tested) | 160 req/s | 29.2 ms | 20.9 ms | 1.26 cores | 1.46 cores |
| `refresh` | 1,600 req/s (highest step tested) | 1,600 req/s | 5.7 ms | 14.5 ms | 1.47 cores | 2.47 cores |
| `introspect` | 6,400 req/s | 6,400 req/s | 1.6 ms | 2.7 ms | 0.28 cores | 0.57 cores |
| `userinfo` | 6,400 req/s | 6,400 req/s | 1.7 ms | 2.6 ms | 0.21 cores | 0.51 cores |
| `jwks` | 6,400 req/s | 6,400 req/s | 1.1 ms | 1.9 ms | 0.15 cores | 0.40 cores |

## Memory

## Endpoint by endpoint

### client_credentials

### refresh

A client trades its refresh token for a new set of tokens. On both sides the old refresh token is invalidated on every exchange (rotation is enabled on Keycloak). FerrisKey has a lower median at every step and uses about 40 % less CPU. Its p95 is better at 800 and 1,600 req/s. At 400 req/s an isolated spike takes its p99 to 206 ms, while the neighbouring steps stay under 13 ms. Keycloak tops out at 1,766 req/s. FerrisKey was not tested above 1,600 req/s.

FerrisKey ran with `REFRESH_TOKEN_FORMAT=opaque` (the refresh token is a random string whose hash is stored, instead of a signed JWT) and `REFRESH_TOKEN_COMMIT=async` (rotations are written with `synchronous_commit=off`). Both default to off. With `async`, a database crash can lose the last rotations: each token consumed by a lost rotation works once more and its successor stops working. Revocations stay durable either way.

## Test conditions

- **Cluster:** k3d on OrbStack on a Mac, with 8 vCPUs shared by the load generator, the IAM server and PostgreSQL. Each role has its own k3d node, but the physical cores are shared.
- **IAM server:** 1 replica, 3 CPUs requested, no CPU limit, 1,536 MiB of memory. Keycloak runs in production mode (`start`) with `-XX:ActiveProcessorCount=3`.
- **Database:** PostgreSQL 17 (CloudNativePG), one per system, 1 CPU requested, 3 GiB, `max_connections` 400, on its own node.
- **Load:** k6 at constant arrival rate (open model), 1,000 users, 15 s of warmup then 60 s measured per step.
- **FerrisKey:** image built from `main` at `ace8c1a`, with `REFRESH_TOKEN_FORMAT=opaque` and `REFRESH_TOKEN_COMMIT=async`. Measured on 2026-10-31 with 300 pre-allocated k6 VUs.
- **Keycloak:** image `quay.io/keycloak/keycloak:26.8.1`, realm with `revokeRefreshToken=true` and `refreshTokenMaxReuse=0`. Refresh measured on 2026-10-31 with 300 pre-allocated VUs. The other five endpoints were measured on 2026-10-26, with k6's default number of pre-allocated VUs.

## What this bench does not tell you

- **Shared machine:** load generator, server and database compete for 8 vCPUs. Absolute figures do not transfer to a production cluster; the gaps between the two systems are the reliable part.
- **No CPU limit:** both servers request 3 CPUs without a limit, but Keycloak caps itself at 3 cores through `-XX:ActiveProcessorCount=3` while FerrisKey can use more. FerrisKey used less CPU anyway at every compared step; its highest reading is 3.14 cores, on `password` at 160 req/s.
- **Single run:** each step was measured once. Differences under 1 ms in p50, or under 20 % in p99, are within the probable noise. The 206 ms p99 spike on `refresh` at 400 req/s is one such reading.
- **Two dates for Keycloak:** five of its endpoints come from the 2026-10-26 run with k6's default VU allocation; FerrisKey and the Keycloak `refresh` were measured on 2026-10-31 with 300 pre-allocated VUs.
- **Non-default refresh settings** on the FerrisKey side, described under [refresh](#refresh).
- **Ladders stop early:** FerrisKey was not pushed past 160 req/s on `password` or 1,600 req/s on `refresh`; the table says where each system's limit is known and where it is not.
- **Raw data:** the per-step JSON of the runs stays with the author outside the repository; the report names the three runs it is built from.

## Reproduce

The tooling is in [`k8s/`](https://github.com/ferriskey/IAM-performance-tester/tree/main/k8s) of IAM-performance-tester, with every variable documented in its [README](https://github.com/ferriskey/IAM-performance-tester/blob/main/k8s/README.md). One system runs at a time; `bench.sh` scales the other to zero before each phase.

```bash
cd k8s
./bench.sh platform     # once per cluster: node roles, CNPG, kube-prometheus-stack
./bench.sh deploy       # Postgres x2, FerrisKey, Keycloak
./bench.sh seed         # realm perf, client perf-client, 1000 users, in both systems
./bench.sh run          # every scenario, both systems, about 1h30 worst case
```

## Before 0.10.1

The same bench run on 2026-10-26 against a build from before the 0.10 token-path work (`sha-d73af3e`) showed Keycloak holding twice the load on `refresh` (1,600 against 800 req/s) and on `userinfo` (6,400 against 3,200 req/s), because FerrisKey queried PostgreSQL on every one of those requests. The refresh grant was reworked in [#1875](https://github.com/ferriskey/ferriskey/pull/1875), `userinfo` reuses the authenticated user since [#1863](https://github.com/ferriskey/ferriskey/pull/1863), and sessions and token state are cached between requests since [#1870](https://github.com/ferriskey/ferriskey/pull/1870). All three shipped in 0.10.1, and the tables above are the result.
