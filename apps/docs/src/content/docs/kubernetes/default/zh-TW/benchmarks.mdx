# 基準測試

FerrisKey 0.10.1 和 Keycloak 26.8.1 在同一個 Kubernetes 叢集上以相同的負載規模執行，資源相同，PostgreSQL 設定相同，使用者數相同，覆蓋六個端點：`client_credentials`、`password`、`refresh`、`introspect`、`userinfo` 和 `jwks`。由 Nathaël Bonnal 測量;包含所有步驟的完整報告見 [IAM-performance-tester](https://github.com/ferriskey/IAM-performance-tester/blob/main/reports/2026-10-31-ferriskey-vs-keycloak.md)。

:::callout{variant="info" title="構建測量"}
FerrisKey 是由 `main` 在 `ace8c1a` 上構建的，與 `v0.10.1` 標籤使用相同的程式碼（兩者僅文件不同）。它執行在 `REFRESH_TOKEN_FORMAT=opaque` 和 `REFRESH_TOKEN_COMMIT=async` 上，這兩個設定自 0.10.1 起引入，預設關閉；有關它們的更改，請參見 [重新整理](#refresh)。
:::

<span id="summary" />

## 摘要

- FerrisKey 在所有六個端點上保持與 Keycloak 相同的最高步驟。
- 它幾乎在所有地方比 Keycloak 使用更少的 CPU，通常在相同速率下 CPU 減半。唯一的例外是從 3,200 req/s 開始的 `userinfo`。
- 在 `refresh` 上，800 req/s 時，FerrisKey 的 p95 為 5.7 毫秒，而 Keycloak 為 14.5 毫秒，同時 CPU 使用減少 40%。
- 從 800 req/s 開始，在 `client_credentials` 上，Keycloak 保持較低的尾部延遲（p99）；在 `password` 上也如此，並且在 `introspect` 和 `userinfo` 上從 3,200 req/s 起相同。
- 差距在機器對機器的端點（`client_credentials`、`refresh`、`introspect`、`jwks`）上最為明顯；人類 `password` 登入是 Keycloak 保留下尾的地方。
- FerrisKey 使用的記憶體更少：最多 618 MiB，而 Keycloak 為 823 MiB。

## 持續速率、延遲和 CPU

持續速率是指在錯誤率低於 1% 的條件下，所服務的目標速率至少達到 95% 且 p95 低於 250 毫秒的最高步驟。延遲和 CPU 在 800 req/s 下讀取，`password` 除外（80 req/s），因為 Argon2id 雜湊使每個請求的開銷設計上較高。CPU 指 IAM 伺服器本身的核心數，在測量的一分鐘內取平均值。

| 端點 | FerrisKey 持續效能 | Keycloak 持續效能 | FerrisKey p95 | Keycloak p95 | FerrisKey CPU | Keycloak CPU |
|---|---|---|---|---|---|---|
| `client_credentials` | 3,200 req/s | 3,200 req/s | 2.7毫秒 | 2.0毫秒 | 0.66 核心 | 0.94 核心 |
| `password`（80 req/s） | 160 req/s（測試的最高步長） | 160 req/s | 29.2毫秒 | 20.9毫秒 | 1.26 核心 | 1.46 核心 |
| `refresh` | 1600 req/s（測試的最高步長） | 1,600 req/s | 5.7毫秒 | 14.5毫秒 | 1.47 核心 | 2.47 核心 |
| `introspect` | 6,400 req/s | 6,400 req/s | 1.6毫秒 | 2.7毫秒 | 0.28 核心 | 0.57 核心 |
| `userinfo` | 6,400 req/s | 6,400 req/s | 1.7毫秒 | 2.6毫秒 | 0.21 核心 | 0.51 核心 |
| `jwks` | 6,400 req/s | 6,400 req/s | 1.1毫秒 | 1.9毫秒 | 0.15 核心 | 0.40 核心 |

### 重新整理

客戶端用重新整理權杖換取一組新權杖。雙方的舊重新整理權杖在每次交換中都失效（Keycloak 啟用輪換）。FerrisKey 在每步的中位數較低，CPU 消耗約 40%。其 p95 在 800 和 1,600 req/s 上表現更好。在 400 req/s 時，孤立的峰值將 p99 提升至 206 毫秒，而鄰近步數保持在 13 毫秒以下。Keycloak 最高為 1,766 req/s。FerrisKey 未測試超過 1,600 req/s。

FerrisKey 執行時有 `REFRESH_TOKEN_FORMAT=opaque`（重新整理權杖是隨機字串，其雜湊值被儲存，而不是有符號的 JWT）和 `REFRESH_TOKEN_COMMIT=async`（輪換用 `synchronous_commit=off` 寫入）。兩者預設都是關閉狀態。使用 `async` 時，資料庫崩潰可能會丟失最後的輪次：每個因失去旋轉而消耗的權杖都會重新工作，其後一個權杖則停止工作。無論哪種方式，撤銷都保持持久。

## 測試條件

- **叢集：** 在 Mac 上的 OrbStack 上執行 k3d，負載發生器、IAM 伺服器和 PostgreSQL 共享 8 個 vCPU。每個角色都有自己的 k3d 節點，但物理核心是共享的。
- **IAM 伺服器：** 1個副本，請求3個CPU，無CPU限制，1,536 MiB記憶體。Keycloak在生產模式（`start`）執行，`-XX:ActiveProcessorCount=3`。
- **Database：** PostgreSQL 17（CloudNativePG），每個系統一個，1個CPU，3GiB，`max_connections` 400個，在獨立節點上。
- **負載：** k6 以恆定到達率（開放型號），1000名使用者，預熱15秒，然後每步測量60秒。
- **FerrisKey：** 使用 `main` 在 `ace8c1a` 構建的映象，搭配 `REFRESH_TOKEN_FORMAT=opaque` 和 `REFRESH_TOKEN_COMMIT=async`。於 2026-10-31 以 300 個預分配的 k6 VU 測量。
- **Keycloak：** 映象 `quay.io/keycloak/keycloak:26.8.1`，身分域包含 `revokeRefreshToken=true` 和 `refreshTokenMaxReuse=0`。重新整理於 2026-10-31 使用 300 個預分配 VU 測量。其他五個端點於 2026-10-26 測量，使用 k6 預設數量的預分配 VU。

<span id="what-this-bench-does-not-tell-you" />

## 此基準測試未告訴您的內容

- **共享機器：** 負載生成器、伺服器和資料庫爭用 8 個 vCPU。絕對數值無法直接應用於生產叢集；兩套系統之間的差距才是可靠的部分。
- **無 CPU 限制：** 兩臺伺服器都請求 3 個 CPU 且無上限，但 Keycloak 透過 `-XX:ActiveProcessorCount=3` 將自己限制在 3 核，而 FerrisKey 可以使用更多。無論如何，在每個比較步驟中 FerrisKey 的 CPU 使用都更少；其最高讀取為 3.14 核，在 `password` 上以 160 req/s 測得。
- **單次執行：** 每個步驟僅測量一次。p50 小於 1 毫秒或 p99 小於 20% 的差異屬於可能的噪聲。在 `refresh` 上以 400 req/s 測得的 206 ms p99 峰值就是這樣的讀數。
- **Keycloak 的兩個日期：** 其五個端點來自 2026-10-26 的執行，使用 k6 預設的 VU 分配；FerrisKey 和 Keycloak `refresh` 則在 2026-10-31 測量，預分配 300 個 VU。
- **非預設重新整理設定**在 FerrisKey 端，如 [refresh](#refresh) 所述。
- **梯子提前停止：** FerrisKey 在 `password` 上沒有超過 160 請求/秒，在 `refresh` 上沒有超過 1,600 請求/秒；表格顯示了每個系統已知的限制和未知的限制。
- **原始資料：** 每一步的 JSON 資料保留在作者手中，不在倉庫中；報告列出了它所基於的三個執行。

## 復現

工具位於 IAM-performance-tester 的 [`k8s/`](https://github.com/ferriskey/IAM-performance-tester/tree/main/k8s) 中，每個變數都在其 [README](https://github.com/ferriskey/IAM-performance-tester/blob/main/k8s/README.md) 中有文件說明。每次只執行一個系統；`bench.sh` 在每個階段前將另一個系統縮放到零。

```bash
cd k8s
./bench.sh platform     # once per cluster: node roles, CNPG, kube-prometheus-stack
./bench.sh deploy       # Postgres x2, FerrisKey, Keycloak
./bench.sh seed         # realm perf, client perf-client, 1000 users, in both systems
./bench.sh run          # every scenario, both systems, about 1h30 worst case
```

## 在 0.10.1 之前

在 2026-10-26 使用 0.10 版本 token-path 工作之前的構建（`sha-d73af3e`）執行相同的基準測試顯示，Keycloak 在 `refresh` 上的負載是之前的兩倍（1,600 對 800 req/s），在 `userinfo` 上也是兩倍（6,400 對 3,200 req/s），因為 FerrisKey 對每一個請求都會查詢 PostgreSQL。重新整理授權在 [#1875](https://github.com/ferriskey/ferriskey/pull/1875) 中進行了重構，`userinfo` 自 [#1863](https://github.com/ferriskey/ferriskey/pull/1863) 起復用了已認證的使用者，並且會話和權杖狀態在請求之間被快取，自 [#1870](https://github.com/ferriskey/ferriskey/pull/1870) 起。以上三個功能都在 0.10.1 中釋出，上表顯示了結果。
