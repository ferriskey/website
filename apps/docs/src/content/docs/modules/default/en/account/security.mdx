# Account security

The credential operations a user performs on their own account. Each one needs an [elevation](/en/modules/account/overview#sensitive-operations-need-an-elevation): a five-minute proof, bound to the calling session, obtained from `POST /users/me/reauthenticate`. A wrong proof counts toward the account lockout like a wrong password does.

Throughout this page, `{realm}` stands for `/realms/{realm_name}`.

## Changing the password

```
PUT {realm}/users/me/password
```

```json title="Request body"
{
  "elevation_id": "01a0d3dd-a750-7f0f-91d9-cf05f19168c6",
  "current_password": "...",
  "new_password": "..."
}
```

The call takes an `elevation_id` like every other sensitive operation, but any live elevation will do, including one proved with a TOTP code. The current password in the body is itself the primary proof, so demanding a password-proved elevation on top would only make the user type it twice. An account that signs in through an external directory has no local password and gets a 409.

The new password is checked against the realm's [password policy](/en/discover/core-concepts/password-policy). The console evaluates the same rules as you type, against `GET {realm}/password-policy/public`, so the failure is visible before submitting rather than after.

<Callout variant="warning" title="Other sessions are signed out">

A successful change revokes the account's other sessions and keeps the current one. That is the intended behaviour for a password change: if the reason for changing it is that someone else has it, leaving their session alive would defeat the exercise. Warn the user in your own UI if you build one, because a silent sign-out of their phone reads as a bug.

</Callout>

## Listing credentials

```
GET {realm}/users/me/credentials
```

Returns what is attached to the account so a UI can show it before offering to add or remove anything. Each entry has `id`, `credential_type`, `label` and `created_at`. The types are `password`, `otp`, `webauthn-public-key-credential` for a passkey, and `recovery-code`, with one entry for each unused [recovery code](/en/modules/trident/recovery-codes). Secrets are never returned. A passkey comes back as its metadata and its id, which is what `DELETE` takes.

## Authenticator app (TOTP)

Enrolment is two calls, because the server must not trust that the user successfully stored the secret until they prove they can read a code from it.

::::step-group
:::step{title="Start the enrolment"}
```
POST {realm}/users/me/mfa/otp
```

The body is `{ "elevation_id": "..." }`, and the elevation must be password-proved. The response carries the `secret` and the `otpauth_uri` to render as a QR code. FerrisKey keeps the secret on the server for 10 minutes, so the confirmation never repeats it. The parameters are fixed at SHA-1, six digits and a thirty-second period, as described in [TOTP](/en/modules/trident/totp).
:::

:::step{title="Confirm with a code"}
```
PUT {realm}/users/me/mfa/otp
```

The body is `{ "elevation_id": "...", "code": "123456", "label": "Alice's phone" }`, and `label` is optional. The elevation must be password-proved. Until this call succeeds, the authenticator is not active and the account's sign-in is unchanged, so an abandoned enrolment leaves nothing behind.

The pending secret is single-use. The call consumes it whether or not the code is right, so a wrong code answers 401 and the user has to start again. A valid code replaces any authenticator the account already had.
:::

:::step{title="Remove it, later"}
```
DELETE {realm}/users/me/mfa/otp
```

The body is `{ "elevation_id": "..." }`. It needs a password-proved elevation. An OTP code is not accepted as the proof for removing OTP.
:::
::::

## Passkeys

Passkey registration follows WebAuthn, so it is also two calls: the browser needs a server challenge, and the server needs the browser's attestation back.

::::step-group
:::step{title="Ask for registration options"}
```
POST {realm}/users/me/passkeys/options
```

The body is `{ "elevation_id": "..." }`, and the elevation must be password-proved. Returns the `PublicKeyCredentialCreationOptions` to hand to `navigator.credentials.create()`, excluding the passkeys the account already holds. The challenge is stored on the server and lives 5 minutes, so it cannot be replayed.
:::

:::step{title="Send the credential back"}
```
POST {realm}/users/me/passkeys
```

The body is `{ "elevation_id": "...", "credential": { ... } }`, where `credential` is the browser's response. The elevation must be password-proved. The server consumes the stored challenge, checks the response against it and against the relying-party ID, then attaches the passkey to the account. An expired or missing challenge, or a response that does not match, is refused.
:::

:::step{title="Delete one"}
```
DELETE {realm}/users/me/passkeys/{credential_id}
```

`credential_id` comes from the credentials listing. The body is `{ "elevation_id": "..." }`, and the elevation must be password-proved. An id that belongs to someone else, or to a credential that is not a passkey, answers 404.
:::
::::

The relying-party ID is the hostname of the web app URL, so a passkey registered through one hostname does not work through another. [WebAuthn](/en/modules/trident/webauthn#where-the-origin-comes-from) explains where the origin comes from.

<Callout variant="info" title="Registration does not check passkey_enabled">

`passkey_enabled` decides whether the sign-in page shows a passkey button. Registering a passkey on a realm where the setting is off still works, but the sign-in page gives the user no way to use it.

</Callout>

## What a removal is refused for

Removing the authenticator or a passkey answers 409 when it would leave the account with no way to sign in: no password, no other passkey and no federated identity. Removing the authenticator also answers 409 when the realm or one of the user's roles has `require_mfa`, because that would drop the second factor they must have. Removing a passkey never trips the second rule, since only an authenticator satisfies it.

## Endpoint summary

| Method | Path | Elevation required |
|---|---|---|
| `GET` | `{realm}/users/me` | None |
| `PUT` | `{realm}/users/me` | None |
| `PUT` | `{realm}/users/@me/locale` | None |
| `POST` | `{realm}/users/me/reauthenticate` | None, it produces the elevation |
| `PUT` | `{realm}/users/me/password` | Any live elevation, plus the current password in the body |
| `GET` | `{realm}/users/me/credentials` | None |
| `POST` | `{realm}/users/me/mfa/otp` | Password-proved |
| `PUT` | `{realm}/users/me/mfa/otp` | Password-proved |
| `DELETE` | `{realm}/users/me/mfa/otp` | Password-proved |
| `POST` | `{realm}/users/me/passkeys/options` | Password-proved |
| `POST` | `{realm}/users/me/passkeys` | Password-proved |
| `DELETE` | `{realm}/users/me/passkeys/{credential_id}` | Password-proved |
| `GET` | `{realm}/users/{user_id}/sessions` | None, for the caller's own id |
| `DELETE` | `{realm}/users/{user_id}/sessions/{session_id}` | None, for the caller's own id |

No permission governs the `/users/me` calls. The token identifies the subject, and the subject is the target. The two session calls take the caller's own id without a permission and need `manage_users` for anyone else's, as described in [Account](/en/modules/account/overview#sessions).

## What gets recorded

<Callout variant="warning" title="The credential operations are not in the audit log">

The self-service credential operations do not write a [SeaWatch](/en/modules/seawatch/overview) security event. A user rotating their own password, enrolling an authenticator or deleting a passkey leaves no entry in the realm's audit trail, and no [webhook](/en/modules/webhooks/overview) fires.

The administrative equivalents do: an admin resetting a password raises `password_reset`, and deleting a user's credential fires the `user.credentials.deleted` webhook trigger. If you need self-service credential changes on the audit trail today, capture them at your own edge. Revoking a session is the exception on the self-service side: it writes a `session_revoked` event.

</Callout>
