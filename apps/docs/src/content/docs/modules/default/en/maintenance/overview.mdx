# Maintenance mode

Maintenance mode temporarily restricts who can authenticate through a client, without touching the client's configuration. It exists for the window where an application is mid-migration and should not be letting users in, but you do not want to disable the client and then try to remember exactly how it was set up.

Two things make it different from disabling a client:

- It is reversible by one switch, and it changes nothing else. Redirect URIs, scopes and secrets all stay as they are.
- It has a hole in it, on purpose. A whitelist of users and roles keeps authenticating, so your own team can verify the migration on the real client before reopening it.

## Closing a client

<img class="only-light" src="/dashboard/client_maintenance-light.jpg" alt="FerrisKey client maintenance tab showing the maintenance switch, reason, session strategy and allowed users" />
<img class="only-dark" src="/dashboard/client_maintenance-dark.jpg" alt="FerrisKey client maintenance tab showing the maintenance switch, reason, session strategy and allowed users" />

```
PUT /realms/{realm_name}/clients/{client_id}/maintenance
```

```json title="Request body"
{
  "enabled": true,
  "reason": "Migration under way, back at 2pm.",
  "session_strategy": "expire"
}
```

| Field | Default | Description |
|---|---|---|
| `enabled` | required | `true` closes the client to everyone but the whitelist |
| `reason` | none | Message shown to blocked users. Without one, they see "This service is currently under maintenance" |
| `session_strategy` | `expire` | `expire` or `terminate`. See below |

The switch applies as soon as you flip it. There is no drain period.

<Callout variant="info" title="Write the reason as the user will read it">

`reason` is what a blocked user is told, and they were trying to get on with their day. "Migration under way, back at 2pm" answers their actual question. "MAINT-4417" does not.

</Callout>

## What maintenance blocks

Maintenance gates the moment a user gets in. A user who is not on the whitelist is refused with the `reason`, whichever way the sign-in completes. The login page's `authenticate` call answers 503:

| Way in | Blocked |
|---|---|
| Password sign-in on the login page | Yes |
| The password grant (`grant_type=password`) | Yes |
| Coming back through an existing SSO session | Yes |
| Answering the second-factor challenge: TOTP code or recovery code | Yes |
| Finishing a required action at sign-in: OTP or passkey enrolment, a forced password update | Yes |
| Passkey sign-in | Yes |
| Magic link | Yes |
| Password reset that continues the original sign-in (`login_url`) | Yes |
| Sign-in through an identity provider (broker) | Yes |
| Device flow, when the device collects its tokens | Yes |

Every login completion goes through the same check, so a path that skips the password does not skip maintenance. The device flow is the odd one out: the check runs when the device collects its tokens, after the user approved the code, and the refusal comes back as a 500 `token_issuance_failed` that quotes the reason. The code is already spent by then, so the device has to start over.

The token response that `reset-password` returns in its body is issued without a client, so maintenance does not apply to it.

Maintenance does not touch sessions that already exist. A refresh token keeps refreshing, and an access token stays valid until it expires, because the check runs at sign-in and not on each request. A `client_credentials` token has no user behind it and is not affected.

### Session strategy

`session_strategy` takes `expire` (the default) or `terminate`, and the console shows it as "Expire naturally" and "Terminate immediately". In FerrisKey 0.10.0 the server stores the value on the client and writes it into the audit event, but the sign-in checks never read it. Under both values, sessions opened before maintenance began keep working until they run out.

<Callout variant="warning" title="terminate does not cut sessions yet">

If you close a client because a token leaked, do not rely on `terminate`. Revoke the sessions that matter with `DELETE /realms/{realm_name}/users/{user_id}/sessions/{session_id}`, which needs `manage_users` and invalidates that session's tokens at once.

</Callout>

## The whitelist

Whitelist entries name a user or a role. Everyone named, and every holder of a named role, authenticates normally while the client is in maintenance.

Entries exist at two levels, and they **add up**: a client's effective whitelist is its own entries plus the realm's.

### Per client

```
GET    /realms/{realm_name}/clients/{client_id}/maintenance/whitelist
POST   /realms/{realm_name}/clients/{client_id}/maintenance/whitelist
DELETE /realms/{realm_name}/clients/{client_id}/maintenance/whitelist/{entry_id}
```

### Per realm

Realm-level entries are inherited by every client of the realm placed under maintenance. They are the standing list of people who should never be locked out.

<img class="only-light" src="/dashboard/realm_maintenance-light.jpg" alt="FerrisKey realm settings maintenance tab showing default maintenance members for users and roles" />
<img class="only-dark" src="/dashboard/realm_maintenance-dark.jpg" alt="FerrisKey realm settings maintenance tab showing default maintenance members for users and roles" />

```
GET    /realms/{realm_name}/settings/maintenance/whitelist
POST   /realms/{realm_name}/settings/maintenance/whitelist
DELETE /realms/{realm_name}/settings/maintenance/whitelist/{entry_id}
```

```json title="Adding an entry: supply one or the other"
{
  "role_id": "01a0d3dd-a750-7817-aa2b-7e8b98f68e66"
}
```

Both `user_id` and `role_id` are optional in the payload; supply the one that describes the entry you want.

<Callout variant="warning" title="Put the role on the realm whitelist before you need it">

A role-based realm entry, your platform team's role for example, is the difference between a planned maintenance window and an incident. Adding a whitelist entry requires authenticating to the admin console, and if the console's own client is the one you just closed, you have locked yourself out of the tool you need to unlock it.

</Callout>

## Permissions

| Action | Permission |
|---|---|
| Read a whitelist | `view_clients`, or `manage_clients` |
| Toggle maintenance, add or remove entries | `manage_clients` |

`manage_realm` also grants all of them.

## What gets recorded

Both transitions are observable, which matters because maintenance mode gets left on by accident:

- [SeaWatch](/en/modules/seawatch/event-types) records `client_maintenance_enabled` and `client_maintenance_disabled`.
- [Webhooks](/en/modules/webhooks/triggers) fire `client.maintenance.enabled` and `client.maintenance.disabled`.

A webhook on the enabled trigger that opens a reminder, and one on disabled that closes it, is the cheapest way to stop a Friday-afternoon window from lasting until Monday.
