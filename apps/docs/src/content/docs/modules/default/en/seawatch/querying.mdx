# Querying events

SeaWatch events are stored in PostgreSQL and read back through one endpoint. It is read-only: there is no endpoint that writes an event, and none that exports them. To move events elsewhere, page through the listing.

The Sea Watch page of the console lists the same events, most recent first. Event, Outcome, Actor and Target each have a filter in their column header, and a single search box above the table matches the IP address. The server applies the filters and the sort to every recorded event, not only to the page on screen.

## The endpoint

```
GET /realms/{realm_name}/seawatch/v1/security-events
```

Reading events needs `view_events`, `manage_events` or `manage_realm`.

:::callout{variant="warning"}
Paths here are written as the server exposes them with no root path, which is the default. Set `SERVER_ROOT_PATH` (the Helm chart sets `/api`) and every path below gains that prefix.
:::

### Parameters

The listing follows the shared contract described in [Paginated listings](/en/discover/guides/api-listings): `page`, `limit`, `order_by`, `order`, filters, and a `{data, metadata}` response.

| Parameter | Type | Description |
|---|---|---|
| `page` | integer, 1 or more | Page number. Defaults to 1 |
| `limit` | integer, 1 to 100 | Page size. Defaults to 20 |
| `order_by` | `event_type`, `status`, `timestamp` or `created_at` | Sort column. Defaults to `created_at` |
| `order` | `asc` or `desc` | Sort direction. Defaults to `desc` |
| `event_types` | comma-separated list | Keeps events of any of these types. An unknown value, or `unknown`, gives 400 |
| `status` | `success` or `failure` | Exact match |
| `actor_id` | UUID | Events made by this account |
| `client_id` | UUID | Events whose target is this UUID. Despite the name it matches `target_id`, so it finds events about a user, a client or a session alike |
| `target_type` | string | Exact match on the target type, for example `user` or `client` |
| `ip_address` | string | Case-insensitive match anywhere in the address. Events without an address never match |
| `search` | string | Same match as `ip_address` |
| `from_timestamp` | RFC 3339 date-time | Events at or after this instant, on `timestamp` |
| `to_timestamp` | RFC 3339 date-time | Events at or before this instant, on `timestamp` |

Filters combine with AND, and a filter sent with an empty value is ignored. `timestamp` is when the event was created. `created_at`, which you can sort on but which is not in the payload, is when it was stored, and it follows the order of the hash chain.

Any other parameter is refused. That includes `offset`, which this endpoint does not have: use `page`. The error names the parameter:

```json title="400 Bad Request"
{
  "code": "E_BAD_REQUEST",
  "status": 400,
  "reason": "invalid_query",
  "message": "Invalid query parameter `offset`: unknown field `offset`, expected one of `search`, `actor_id`, `client_id`, `event_types`, `status`, `target_type`, `from_timestamp`, `to_timestamp`, `ip_address`"
}
```

### Examples

Failed sign-ins in a window, newest first:

```bash
curl -G "http://localhost:3333/realms/my-app/seawatch/v1/security-events" \
  --data-urlencode "event_types=login_failure" \
  --data-urlencode "from_timestamp=2026-10-01T00:00:00Z" \
  --data-urlencode "to_timestamp=2026-10-31T23:59:59Z" \
  --data-urlencode "limit=100" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

Everything one account did, oldest first:

```bash
curl -G "http://localhost:3333/realms/my-app/seawatch/v1/security-events" \
  --data-urlencode "actor_id=USER_UUID" \
  --data-urlencode "order_by=timestamp" \
  --data-urlencode "order=asc" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

Several event types at once:

```bash
curl -G "http://localhost:3333/realms/my-app/seawatch/v1/security-events" \
  --data-urlencode "event_types=client_secret_viewed,role_permission_updated,role_assigned" \
  -H "Authorization: Bearer $ADMIN_TOKEN"
```

## Questions the filters answer

| Question | Parameters |
|---|---|
| Who changed the roles of this user? | `event_types=role_assigned,role_unassigned` and `client_id=USER_UUID`. `actor_id` of each result is the administrator, and `resource` is the role name |
| Who read the secret of this client? | `event_types=client_secret_viewed` and `client_id=CLIENT_UUID` |
| When was this client in maintenance? | `event_types=client_maintenance_enabled,client_maintenance_disabled` and `client_id=CLIENT_UUID` |
| What did this administrator do last month? | `actor_id=ADMIN_UUID`, `from_timestamp` and `to_timestamp` |
| Which accounts were created or deleted this quarter? | `event_types=user_created,user_deleted`, `from_timestamp` and `to_timestamp` |
| Which sessions did this user open? | `event_types=session_created` and `actor_id=USER_UUID` |
| Which webhook deliveries gave up? | `event_types=webhook_delivery_exhausted` |

`client_id` is the UUID of the client, not its `client_id` string. A bulk user deletion has no target, so it does not appear under a user's `client_id`.

## Feeding a SIEM

SeaWatch does not push events. [Webhooks](/en/modules/webhooks/triggers) have their own triggers, and sign-ins, sessions and secret reads are not among them. To forward events to Splunk, Elastic, Datadog or any other collector, poll the listing:

1. Request `order_by=created_at`, `order=asc` and `limit=100`, with `from_timestamp` set to the latest `timestamp` you stored, and follow `next_page` until it is null.
2. Deduplicate on `id`. The `from_timestamp` bound is inclusive, so the boundary event comes back.
3. Overlap the window by a few minutes. `timestamp` is set when the event is created and `created_at` when it is stored, so an event can be stored slightly after one that carries a later `timestamp`.

The `trace_id` field is empty, so an event cannot be joined to a trace. To tie a sign-in to its [Compass](/en/modules/compass/querying) flow, match the user and the time: for an interactive sign-in, the flow's `user_id` is the event's `actor_id`, and the event's `timestamp` falls between the flow's `started_at` and `completed_at`.

## Retention

FerrisKey never deletes SeaWatch events. The table grows for the life of the deployment, and its size is yours to plan for.

Do not remove old rows to save space. Each event is chained to the one before it, so the oldest remaining event would no longer start from the zero hash and the gap would read as tampering. Copy events to long-term storage through the listing and leave the originals in place.
