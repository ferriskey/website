# Password Policy

Each realm carries its own password policy, stored separately from the rest of the realm settings and edited on its own screen. It is enforced everywhere a password is set: registration, an administrative reset, the reset link a user receives by email, the update a required action asks for, and a user changing their own password.

## The rules

A realm that has never saved a policy uses the defaults below. They follow [CNIL deliberation 2022-100](https://www.legifrance.gouv.fr/jorf/id/JORFTEXT000046444507): at least 12 characters, all four character classes, and 80 bits of entropy.

| Field | Default | Description |
|---|---|---|
| `min_length` | `12` | Minimum length. The API accepts 1 to 128 |
| `require_uppercase` | `true` | At least one uppercase letter |
| `require_lowercase` | `true` | At least one lowercase letter |
| `require_number` | `true` | At least one digit |
| `require_special` | `true` | At least one character that is neither a letter nor a digit |
| `max_age_days` | none | Stored and returned, but not applied. See [Expiry is stored, not applied](#expiry-is-stored-not-applied) |
| `min_entropy_bits` | `80` | Reject passwords below this estimated entropy. `0` disables the check, the API accepts 0 to 256 |
| `forbid_common` | `true` | Reject a password that is on the built-in list of 100 common passwords, or equal to the username or to the part of the email address before the `@` |
| `check_breached` | `false` | Stored, but 0.10.0 has no breach lookup, so turning it on changes nothing |

A `PUT` takes any subset of these fields and leaves the others as they are.

When a password breaks the policy, the response is a `422` that lists every broken rule at once, one entry per rule, with a stable `code`:

```json title="PUT /realms/{realm_name}/users/{user_id}/reset-password"
{
  "errors": [
    { "field": "password", "code": "too_short", "message": "Password is too short: 10 characters (minimum 12 required)" },
    { "field": "password", "code": "missing_uppercase", "message": "Password must contain at least one uppercase letter" },
    { "field": "password", "code": "missing_special", "message": "Password must contain at least one special character" },
    { "field": "password", "code": "insufficient_entropy", "message": "Password is not strong enough. Make it longer, or mix uppercase and lowercase letters, numbers and symbols" }
  ]
}
```

The other codes are `missing_lowercase`, `missing_number` and `common_password`. Match on `code`, not on `message`; see [API errors](/en/discover/guides/api-errors).

## Entropy is the rule that does the real work

The four character-class requirements are the familiar ones, and they are also the weakest. `Passw0rd!` satisfies every one of them. With the defaults it is rejected by two other rules: it has 9 characters, and its estimated entropy is about 59 bits.

FerrisKey estimates entropy as the length times the base-2 logarithm of a character pool. The pool adds 26 for lowercase letters, 26 for uppercase, 10 for digits and 33 for symbols, counting each class the password uses. That makes the default 80 bits stricter than 12 characters suggests: 12 characters from all four classes score 78.8 bits, so with the defaults a password needs 13.

Two things follow:

- If you raise entropy, you can relax the character classes. With only lowercase letters, 18 characters reach 80 bits and 17 do not (79.9). A long passphrase clears the bar and contains no symbol. Requiring one pushes users toward `Password1!` rather than toward something strong.
- The estimate only counts ASCII characters, and it counts length in bytes. A password made only of non-ASCII characters, for example in Chinese, scores 0 bits and fails any entropy threshold above 0.

`forbid_common` is a narrow check. It compares the whole password, ignoring case, with a list of 100 entries and with the username and email local part. `password1` is on the list, `Password1!` is not.

## Expiry is stored, not applied

`max_age_days` reads back as `null` until you set it, and the API accepts 0 or more. The console shows it as Password Expiry and describes a forced change after that many days, but nothing in the sign-in path of 0.10.0 reads the value. A password does not expire because of its age.

To make someone change a password, reset it with `temporary: true`. The user is sent to the `update_password` required action at their next sign-in. See [Users](/en/discover/core-concepts/users#administering-a-user).

## The public endpoint

```
GET /realms/{realm_name}/password-policy/public
```

Unauthenticated, and it returns five fields: `min_length`, `require_uppercase`, `require_lowercase`, `require_number` and `require_special`. The entropy, common-password and breach settings are not part of it, so a form can list the character rules next to the field but learns about the others only from the `422` after submitting.

This is what lets a registration or reset form show the rules instead of rejecting the user after a round trip. Use it rather than hard-coding the rules in your frontend: the realm's policy can change, and a form that checks a stale copy tells users their password is fine and then watches the server refuse it.

## API reference

| Method | Path | Description |
|---|---|---|
| `GET` | `/realms/{realm_name}/password-policy` | Read the full policy |
| `PUT` | `/realms/{realm_name}/password-policy` | Update the policy |
| `GET` | `/realms/{realm_name}/password-policy/public` | Read the five public rules, unauthenticated |

**Required permissions:** `manage_realm`, for the read as well as the update. The public endpoint needs none.

<Callout variant="info" title="Changing the policy does not invalidate existing passwords">

A stricter policy applies to the next password each user sets. Passwords already stored keep working, and nothing scans them against the new rules.

</Callout>

## Imported passwords

Passwords migrated from another IAM are a special case. FerrisKey accepts a hash on import and keeps it as the user's password credential. The first time the user signs in successfully, it re-hashes the password with argon2id: the plaintext is only available at that moment.

The policy is not applied to an imported password, since FerrisKey never sees the plaintext. It applies when that user next changes it. The import raises one `password_imported` event in [SeaWatch](/en/modules/seawatch/event-types) when an administrator calls the import endpoint. The upgrade at first sign-in raises nothing. See [Export & Import](/en/discover/guides/portability#password-hashes).
