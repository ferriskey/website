# 静态存储密钥

FerrisKey 数据库中的某些值可以被任何复制它们的人使用：签署身份域令牌的私钥、用户身份认证器应用程序背后的种子，以及发送邮件的 SMTP 账户密码。设置 `SECRETS_ENCRYPTION_KEYS` 后，FerrisKey 会在写入之前加密这些值，因此数据库转储或被窃取的备份不会泄露它们。

如果不设置该变量，它们将保持明文。每次启动时 API 都会记录警告。

<span id="what-is-sealed" />

## 什么是密封

FerrisKey 将加密的值称为**密封**。目前只有四列是密封的。其他所有内容无论有无密钥，格式都保持原样。

| 密钥 | 它的位置 | 密封 |
|---|---|---|
| 身份域签名私钥 | `jwt_keys.private_key` | 是 |
| TOTP 凭据（认证器种子） | `credentials.secret_data`，用于 `otp` 类型的凭据 | 是 |
| 正在进行中的 TOTP 注册 | `otp_enrollments.secret` | 是 |
| 一个身份域的 SMTP 密码 | `smtp_configs.password` | 是 |
| 身份提供者客户端密钥 | `identity_providers.config`（JSON） | 否。以明文存储，当 API 返回时显示为 `***` |
| LDAP 绑定密码 | `user_federation_providers.config`（JSON） | 否。按原样存储，在 API 响应中屏蔽 |
| 客户端密钥 | `clients.secret` | 不 |
| Webhook 签名密钥 | `webhooks.secret` | 不 |

屏蔽只改变 API 显示的内容。它不会改变数据库中的内容，因此任何能读取该表的人都能读取身份提供者密钥。

LDAP绑定密码存放在名为`bind_password_encrypted`的字段中，但没有任何加密：LDAP客户端会获取存储的值，如果可以则解码为base64，否则按明文使用。将其视为明文密钥。

用户密码情况不同。它们以单向哈希存储，而不是可以读取的密钥，并且封存扫描会跳过它们。

<span id="generate-the-keys" />

## 生成密钥

一个密钥是32个随机字节，用base64表示。OpenSSL可以生成一个：

```bash
openssl rand -base64 32
```

`SECRETS_ENCRYPTION_KEYS`保存一个或多个密钥，每个密钥用`id:base64`表示，并用逗号分隔：

```text
SECRETS_ENCRYPTION_KEYS=2026-10:<output of openssl rand -base64 32>
```

ID是你选择的标签。它可以包含字母、数字、`-`和`_`，并且每个ID必须唯一。FerrisKey会将其写在每个封存值前，以便知道使用哪个密钥打开它。

如果条目没有 `:`，或者 ID 使用了其他字符或出现两次，或者密钥不是有效的 base64，或者解码后不是恰好 32 字节，服务器将拒绝启动。

通过环境变量传递该变量。`--secrets-encryption-keys` 标志也可以使用，但标志会显示在进程列表中。

:::codegroup
```yaml [Docker Compose]
services:
  api:
    environment:
      SECRETS_ENCRYPTION_KEYS: ${SECRETS_ENCRYPTION_KEYS}
```

```yaml [Kubernetes Secret]
apiVersion: v1
kind: Secret
metadata:
  name: ferriskey-secrets-encryption
type: Opaque
stringData:
  SECRETS_ENCRYPTION_KEYS: "2026-10:<output of openssl rand -base64 32>"
```

```yaml [Helm values]
api:
  env:
    - name: SECRETS_ENCRYPTION_KEYS
      valueFrom:
        secretKeyRef:
          name: ferriskey-secrets-encryption
          key: SECRETS_ENCRYPTION_KEYS
```
:::

在 Compose 中，`${SECRETS_ENCRYPTION_KEYS}` 引用从你的 shell 或 Compose 文件旁边的 `.env` 文件读取值。Helm Chart通过 `api.env` 和 `api.envFrom` 向 API 容器传递额外变量；其余Chart请参见 [Helm Chart](/zh-CN/kubernetes/helm-chart) 页面。

将密钥保存在数据库之外，并单独备份。恢复的数据库仅能使用封存它的密钥读取。

<span id="how-a-value-is-sealed" />

## 值是如何被封存的

FerrisKey 使用 AES-256-GCM，并为每个值生成新的随机 nonce。密封的值如下所示：

```text
fk1:2026-10:<base64url of nonce, ciphertext and tag>
```

列名和行 ID 会与数据一起进行认证。复制到另一行或另一列的密封值无法解开，原地修改的值也一样无法解开。

<span id="turning-it-on-for-an-existing-deployment" />

## 为现有部署开启该功能

在启动 API 时设置该变量。在接受请求之前，FerrisKey 会以 200 条为批次遍历四个列，并对仍为明文的每个值进行密封。从那时起，写入的新值都会被密封。

关于该扫描流程的两个细节：

- 无法密封的值会以错误级别记录并跳过。服务器仍会启动，下次启动时会再次尝试该值。
- 如果清扫在数据库错误时失败，服务器会记录日志并仍然启动。未封闭的值将在下一次启动时重试。

第一次启动后检查日志。`sealed the stored secrets that were not under the active key` 行会报告每种类型有多少值被封闭。

<span id="rotating-a-key" />

## 旋转密钥

列表中的第一个密钥用于封闭，而列表中的每个密钥都可以打开。要旋转密钥，请将新密钥放在第一位，并将旧密钥放在它之后：

```text
SECRETS_ENCRYPTION_KEYS=2027-04:<new key>,2026-10:<old key>
```

在下次启动时，FerrisKey 会重新封闭所有不在新第一密钥下的值。一旦每个副本在新列表上启动完毕，你就可以删除旧密钥。

对于多个副本，分两次滚动完成。先在列表末尾添加新密钥并展开，让每个副本都能打开。然后把它移到前面，再重新滚动一次。如果你一开始就把它放在前面，第一个开始的副本会重新封印这些值，而仍在运行旧列表的副本就无法打开它们。

:::callout{variant="danger" title="仍在使用的密钥不能掉落"}
移除仍封存部分值的密钥会使这些值无法读取。错误读作`the secret is sealed with key <id>, which is not in the key ring`。完全取消变量则会得到`the secret is sealed but no encryption key is configured`。这两种方法都不会让值恢复清晰：用密封的身份域密钥签署令牌、检查TOTP代码或用密封SMTP密码发送邮件都会失败，直到密钥恢复。保留列表中的所有旧密钥，直到用新的第一个密钥重新封存所有密钥。
:::
