# 靜態儲存金鑰

FerrisKey 資料庫中的某些值可以被任何複製它們的人使用：簽署身分域權杖的私鑰、使用者身分認證器應用程式背後的種子，以及傳送郵件的 SMTP 賬戶密碼。設定 `SECRETS_ENCRYPTION_KEYS` 後，FerrisKey 會在寫入之前加密這些值，因此資料庫轉儲或被竊取的備份不會洩露它們。

如果不設定該變數，它們將保持明文。每次啟動時 API 都會記錄警告。

<span id="what-is-sealed" />

## 什麼是密封

FerrisKey 將加密的值稱為**密封**。目前只有四列是密封的。其他所有內容無論有無金鑰，格式都保持原樣。

| 金鑰 | 它的位置 | 密封 |
|---|---|---|
| 身分域簽名私鑰 | `jwt_keys.private_key` | 是 |
| TOTP 憑據（認證器種子） | `credentials.secret_data`，用於 `otp` 型別的憑據 | 是 |
| 正在進行中的 TOTP 註冊 | `otp_enrollments.secret` | 是 |
| 一個身分域的 SMTP 密碼 | `smtp_configs.password` | 是 |
| 身分提供者客戶端金鑰 | `identity_providers.config`（JSON） | 否。以明文儲存，當 API 返回時顯示為 `***` |
| LDAP 繫結密碼 | `user_federation_providers.config`（JSON） | 否。按原樣儲存，在 API 響應中遮蔽 |
| 客戶端金鑰 | `clients.secret` | 不 |
| Webhook 簽名金鑰 | `webhooks.secret` | 不 |

遮蔽只改變 API 顯示的內容。它不會改變資料庫中的內容，因此任何能讀取該表的人都能讀取身分提供者金鑰。

LDAP繫結密碼存放在名為`bind_password_encrypted`的欄位中，但沒有任何加密：LDAP客戶端會獲取儲存的值，如果可以則解碼為base64，否則按明文使用。將其視為明文金鑰。

使用者密碼情況不同。它們以單向雜湊儲存，而不是可以讀取的金鑰，並且封存掃描會跳過它們。

<span id="generate-the-keys" />

## 生成金鑰

一個金鑰是32個隨機位元組，用base64表示。OpenSSL可以生成一個：

```bash
openssl rand -base64 32
```

`SECRETS_ENCRYPTION_KEYS`儲存一個或多個金鑰，每個金鑰用`id:base64`表示，並用逗號分隔：

```text
SECRETS_ENCRYPTION_KEYS=2026-10:<output of openssl rand -base64 32>
```

ID是你選擇的標籤。它可以包含字母、數字、`-`和`_`，並且每個ID必須唯一。FerrisKey會將其寫在每個封存值前，以便知道使用哪個金鑰開啟它。

如果條目沒有 `:`，或者 ID 使用了其他字元或出現兩次，或者金鑰不是有效的 base64，或者解碼後不是恰好 32 位元組，伺服器將拒絕啟動。

透過環境變數傳遞該變數。`--secrets-encryption-keys` 標誌也可以使用，但標誌會顯示在程序列表中。

:::codegroup
```yaml [Docker Compose]
services:
  api:
    environment:
      SECRETS_ENCRYPTION_KEYS: ${SECRETS_ENCRYPTION_KEYS}
```

```yaml [Kubernetes Secret]
apiVersion: v1
kind: Secret
metadata:
  name: ferriskey-secrets-encryption
type: Opaque
stringData:
  SECRETS_ENCRYPTION_KEYS: "2026-10:<output of openssl rand -base64 32>"
```

```yaml [Helm values]
api:
  env:
    - name: SECRETS_ENCRYPTION_KEYS
      valueFrom:
        secretKeyRef:
          name: ferriskey-secrets-encryption
          key: SECRETS_ENCRYPTION_KEYS
```
:::

在 Compose 中，`${SECRETS_ENCRYPTION_KEYS}` 引用從你的 shell 或 Compose 檔案旁邊的 `.env` 檔案讀取值。Helm Chart透過 `api.env` 和 `api.envFrom` 向 API 容器傳遞額外變數；其餘Chart請參見 [Helm Chart](/zh-TW/kubernetes/helm-chart) 頁面。

將金鑰儲存在資料庫之外，並單獨備份。恢復的資料庫僅能使用封存它的金鑰讀取。

<span id="how-a-value-is-sealed" />

## 值是如何被封存的

FerrisKey 使用 AES-256-GCM，併為每個值生成新的隨機 nonce。密封的值如下所示：

```text
fk1:2026-10:<base64url of nonce, ciphertext and tag>
```

列名和行 ID 會與資料一起進行認證。複製到另一行或另一列的密封值無法解開，原地修改的值也一樣無法解開。

<span id="turning-it-on-for-an-existing-deployment" />

## 為現有部署開啟該功能

在啟動 API 時設定該變數。在接受請求之前，FerrisKey 會以 200 條為批次遍歷四個列，並對仍為明文的每個值進行密封。從那時起，寫入的新值都會被密封。

關於該掃描流程的兩個細節：

- 無法密封的值會以錯誤級別記錄並跳過。伺服器仍會啟動，下次啟動時會再次嘗試該值。
- 如果清掃在資料庫錯誤時失敗，伺服器會記錄日誌並仍然啟動。未封閉的值將在下一次啟動時重試。

第一次啟動後檢查日誌。`sealed the stored secrets that were not under the active key` 行會報告每種型別有多少值被封閉。

<span id="rotating-a-key" />

## 旋轉金鑰

列表中的第一個金鑰用於封閉，而列表中的每個金鑰都可以開啟。要旋轉金鑰，請將新金鑰放在第一位，並將舊金鑰放在它之後：

```text
SECRETS_ENCRYPTION_KEYS=2027-04:<new key>,2026-10:<old key>
```

在下次啟動時，FerrisKey 會重新封閉所有不在新第一金鑰下的值。一旦每個副本在新列表上啟動完畢，你就可以刪除舊金鑰。

對於多個副本，分兩次滾動完成。先在列表末尾新增新金鑰並展開，讓每個副本都能開啟。然後把它移到前面，再重新滾動一次。如果你一開始就把它放在前面，第一個開始的副本會重新封印這些值，而仍在執行舊列表的副本就無法開啟它們。

:::callout{variant="danger" title="仍在使用的金鑰不能掉落"}
移除仍封存部分值的金鑰會使這些值無法讀取。錯誤讀作`the secret is sealed with key <id>, which is not in the key ring`。完全取消變數則會得到`the secret is sealed but no encryption key is configured`。這兩種方法都不會讓值恢復清晰：用密封的身分域金鑰簽署權杖、檢查TOTP程式碼或用密封SMTP密碼傳送郵件都會失敗，直到金鑰恢復。保留列表中的所有舊金鑰，直到用新的第一個金鑰重新封存所有金鑰。
:::
