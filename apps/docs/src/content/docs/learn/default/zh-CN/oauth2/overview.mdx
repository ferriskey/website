# 什么是OAuth2？

OAuth 2.0是一种委托协议。它允许应用代表用户操作，而无需查看该用户的密码。

这一句话作用很大。对它的标准类比是代客泊车钥匙，是的，它被用滥了，但没有其他比喻能如此清晰地表达其意思。

<span id="the-valet-parking-analogy" />

## 代客泊车类比

当你在酒店停车时，你不会把房门钥匙、车钥匙和钱包都交给代客。你只交给他们一把**代客钥匙**。代客钥匙可以启动汽车、打开车门，但别的都不能开。它打不开车后备箱或手套箱。如果代客钥匙丢了，你也不会破产。

OAuth2 发放代客钥匙。它们被称为 **访问令牌**。

- 车主是用户。
- 代客是某个想为用户做事情的应用程序（发推文、读取日历、刷卡）。
- 发放代客钥匙的车库老板是授权服务器。在 FerrisKey 的情况下，就是 FerrisKey 本身。
- 汽车是资源，通常是一个 API。

你发放的钥匙只拥有完成特定工作的最小权限。这就是整个游戏的关键。

<span id="the-four-roles" />

## 四个角色

OAuth2 定义了四个角色。你会在各处看到这些术语：

- **资源所有者**：用户。拥有数据。
- **客户端**：请求访问的应用程序（网页应用、移动应用、服务器）。
- **授权服务器**：用于验证用户身份并颁发令牌的可信服务。这就是 FerrisKey 的功能。
- **资源服务器**：存放用户数据并接受访问令牌的 API。

授权服务器和资源服务器可以是同一个服务，也可以是两个独立的服务。在 OIDC 部署中，它们通常是捆绑在一起的。

<span id="what-oauth2-is-not" />

## OAuth2 不是什么

这很容易让人混淆，所以直接说清楚：

- OAuth2 不是认证协议。它告诉你应用被允许做什么，而不是用户是谁。关于“用户是谁”，你需要 OIDC，它是建立在 OAuth2 之上的。
- OAuth2 没有定义令牌格式。访问令牌可以是随机字符串、JWT 或任何形式。规范对此不关心。
- OAuth2 也不是一个会话协议。它发放令牌后就离开了。客户端如何使用这些令牌是客户端自己的问题。

当有人说“我在用 OAuth2 登录”时，他们几乎总是指 OIDC，只是还不知道而已。

<span id="the-shape-of-an-oauth2-exchange" />

## OAuth2 交换的形式

在最常见的流程（带 PKCE 的授权码流程）中，用户会被重定向经过如下步骤：

```
User → Client → Authorization Server → (user logs in) → Client → Authorization Server → Access Token
```

用户向授权服务器证明他们的身份，而不是向客户端。客户端永远看不到密码。作为回报，客户端会收到一个短期有效的访问令牌，可以用它来访问 API。

不同的情况需要不同的流程。请参见 [Flows](/zh-CN/learn/oauth2/flows) 页面。

<span id="why-oauth2-won" />

## 为什么 OAuth2 赢

在 OAuth2 之前，“使用其他服务登录”是这样的：你在服务 B 中输入服务 A 的密码，然后服务 B 就以你的身份登录。它被称为密码反模式，效果确实如名字听起来一样糟糕。

OAuth2 用受控交接取而代之。服务 B 会把你重定向到服务 A，你在 _那里_ 登录，然后服务 A 把一个权限范围严格限定的令牌交给服务 B。服务 B 永远看不到你的密码。你可以随时撤销它的令牌。

短期、限定权限、可撤销、委托。每一个现代 API 集成都基于这个理念，即便没人再称它为 OAuth2。
