# 什麼是OAuth2？

OAuth 2.0是一種委託協議。它允許應用代表使用者操作，而無需檢視該使用者的密碼。

這一句話作用很大。對它的標準類比是代客泊車鑰匙，是的，它被用濫了，但沒有其他比喻能如此清晰地表達其意思。

<span id="the-valet-parking-analogy" />

## 代客泊車類比

當你在酒店停車時，你不會把房門鑰匙、車鑰匙和錢包都交給代客。你只交給他們一把**代客鑰匙**。代客鑰匙可以啟動汽車、開啟車門，但別的都不能開。它打不開車後備箱或手套箱。如果代客鑰匙丟了，你也不會破產。

OAuth2 發放代客鑰匙。它們被稱為 **存取權杖**。

- 車主是使用者。
- 代客是某個想為使用者做事情的應用程式（發推文、讀取日曆、刷卡）。
- 發放代客鑰匙的車庫老闆是授權伺服器。在 FerrisKey 的情況下，就是 FerrisKey 本身。
- 汽車是資源，通常是一個 API。

你發放的鑰匙只擁有完成特定工作的最小權限。這就是整個遊戲的關鍵。

<span id="the-four-roles" />

## 四個角色

OAuth2 定義了四個角色。你會在各處看到這些術語：

- **資源所有者**：使用者。擁有資料。
- **客戶端**：請求存取的應用程式（網頁應用、移動應用、伺服器）。
- **授權伺服器**：用於驗證使用者身分並頒發權杖的可信服務。這就是 FerrisKey 的功能。
- **資源伺服器**：存放使用者資料並接受存取權杖的 API。

授權伺服器和資源伺服器可以是同一個服務，也可以是兩個獨立的服務。在 OIDC 部署中，它們通常是捆綁在一起的。

<span id="what-oauth2-is-not" />

## OAuth2 不是什麼

這很容易讓人混淆，所以直接說清楚：

- OAuth2 不是認證協議。它告訴你應用被允許做什麼，而不是使用者是誰。關於“使用者是誰”，你需要 OIDC，它是建立在 OAuth2 之上的。
- OAuth2 沒有定義權杖格式。存取權杖可以是隨機字串、JWT 或任何形式。規範對此不關心。
- OAuth2 也不是一個會話協議。它發放權杖後就離開了。客戶端如何使用這些權杖是客戶端自己的問題。

當有人說“我在用 OAuth2 登入”時，他們幾乎總是指 OIDC，只是還不知道而已。

<span id="the-shape-of-an-oauth2-exchange" />

## OAuth2 交換的形式

在最常見的流程（帶 PKCE 的授權碼流程）中，使用者會被重定向經過如下步驟：

```
User → Client → Authorization Server → (user logs in) → Client → Authorization Server → Access Token
```

使用者向授權伺服器證明他們的身分，而不是向客戶端。客戶端永遠看不到密碼。作為回報，客戶端會收到一個短期有效的存取權杖，可以用它來存取 API。

不同的情況需要不同的流程。請參見 [Flows](/zh-TW/learn/oauth2/flows) 頁面。

<span id="why-oauth2-won" />

## 為什麼 OAuth2 贏

在 OAuth2 之前，“使用其他服務登入”是這樣的：你在服務 B 中輸入服務 A 的密碼，然後服務 B 就以你的身分登入。它被稱為密碼反模式，效果確實如名字聽起來一樣糟糕。

OAuth2 用受控交接取而代之。服務 B 會把你重定向到服務 A，你在 _那裡_ 登入，然後服務 A 把一個權限範圍嚴格限定的權杖交給服務 B。服務 B 永遠看不到你的密碼。你可以隨時撤銷它的權杖。

短期、限定權限、可撤銷、委託。每一個現代 API 整合都基於這個理念，即便沒人再稱它為 OAuth2。
