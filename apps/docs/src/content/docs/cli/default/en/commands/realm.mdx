# `realm`

Manage realms, the isolated tenants that hold clients, users, roles, and credentials.

```bash
ferris-ctl realm <subcommand>
```

`get`, `create`, and `delete` take the realm name as an argument. The `role` subcommands act on `--realm`, which defaults to the context's realm. Every subcommand signs in to the context's realm, so the context must have one. See [Authentication](/en/cli/authentication#contexts).

<Callout variant="warning" title="Known limit: only the first page is read">

The server returns lists in pages of 20 by default (100 at most), and `ferris-ctl` reads the first page only. This affects `realm list`, which shows at most 20 realms, and the realm roles: `realm role list` shows the first 20, and `realm role get` and `realm role delete` find a role by name in that page, so they answer `role '<name>' not found` for a role beyond it. `--client <client_id>` resolves the client by `client_id` in the first 20 clients of the realm. The roles of a client are not paged. The API reaches the rest with its `page` and `limit` parameters, and so does the admin console.

</Callout>

## `realm list`

List the realms the signed-in identity may access.

```bash
ferris-ctl realm list
```

Table columns: NAME, ID.

## `realm get`

Show a single realm's id and name.

```bash
ferris-ctl realm get <name>
```

| Argument | Required | Description |
|----------|----------|-------------|
| `<name>` | yes | Realm name |

## `realm create`

Create a new realm and print its id and name.

```bash
ferris-ctl realm create <name>
```

| Argument | Required | Description |
|----------|----------|-------------|
| `<name>` | yes | Name of the realm to create |

## `realm delete`

Delete a realm. This prompts for confirmation, since it also removes the realm's clients, users, and roles.

```bash
ferris-ctl realm delete <name> [--force]
```

| Argument | Required | Description |
|----------|----------|-------------|
| `<name>` | yes | Name of the realm to delete |
| `--force` / `-f` | no | Skip the confirmation prompt |

<Callout variant="warning" title="Confirmation in scripts">

Without `--force`, the command refuses to run in a non-interactive shell rather than deleting silently. Pass `--force` (or `-f`) in CI and automation.

</Callout>

## `realm role`

Manage the roles of a realm, or the roles scoped to one of its clients. Every subcommand takes `--realm` to target a realm other than the context default, and `--client <client_id>` to work on that client's roles instead of the realm's.

### `realm role create`

```bash
ferris-ctl realm role create <name> [--description <text>] [--permission <name>]... [--realm <realm>] [--client <client_id>]
```

| Argument | Required | Description |
|----------|----------|-------------|
| `<name>` | yes | Role name |
| `--description` | no | Free-text description |
| `--permission` | no | A permission granted by the role. Repeat the flag for several |
| `--realm` | no | Realm (defaults to the context realm) |
| `--client` | no | Create a client role scoped to this client id, instead of a realm role |

Permissions are passed by their snake_case name, for example `manage_users`. See the [permissions reference](/en/discover/core-concepts/roles#permissions-reference) for the full list.

```bash title="A realm role that can manage users"
ferris-ctl realm role create user-admin \
  --description "Create and update users" \
  --permission manage_users \
  --permission query_users \
  --permission view_users
```

```bash title="A role scoped to one client"
ferris-ctl realm role create service-reader --client backend
```

<Callout variant="warning" title="You can only grant permissions you hold">

The server lets an identity put on a role only the permissions it holds itself. Without `manage_realm`, a permission you do not hold, or a name FerrisKey does not know, is refused with 403 `cannot grant a permission you do not hold`. With `manage_realm`, any name is accepted, but a name FerrisKey does not recognize is dropped without an error, so a typo gives a role with fewer permissions than you asked for. `realm role get` prints only the id and name, so check the permissions of the new role in the admin console.

</Callout>

### `realm role list`

```bash
ferris-ctl realm role list [--realm <realm>] [--client <client_id>]
```

Lists realm roles, or the roles of `--client` when given. Table columns: NAME, ID.

### `realm role get`

```bash
ferris-ctl realm role get <name> [--realm <realm>] [--client <client_id>]
```

Prints the id and name of the role.

### `realm role delete`

```bash
ferris-ctl realm role delete <name> [--realm <realm>] [--client <client_id>] [--force]
```

| Argument | Required | Description |
|----------|----------|-------------|
| `<name>` | yes | Role name |
| `--realm` | no | Realm (defaults to the context realm) |
| `--client` | no | Delete a client role instead of a realm role |
| `--force` / `-f` | no | Skip the confirmation prompt (required in non-interactive shells) |

## `realm import`

Import a realm (its settings, roles, clients, and users) from a description file, a live Keycloak, a live Zitadel, or a Supabase project.

```bash
ferris-ctl realm import --from <kind> [source flags] [--target-realm <name>] [--dry-run]
```

| Flag | Description |
|------|-------------|
| `--from` | Source kind: `config`, `keycloak`, `zitadel`, or `supabase`. Optional with `--source-ref`, and ignored then: the kind of the stored source wins |
| `--source-ref` | Name of a stored [source](/en/cli/commands/source); inline flags below override its values |
| `--file` | Path to a realm description file (required for `--from config`); `.yaml`, `.yml`, or `.toml` |
| `--source-url` | Base URL of the source instance (Keycloak, Zitadel, Supabase project) |
| `--source-realm` | Keycloak: the realm to read (required). Supabase and Zitadel with a pinned organization: the name of the realm to create |
| `--source-org` | Source organization id (Zitadel); sent as the `x-zitadel-orgid` header |
| `--source-client-id` | Client id for source authentication (Keycloak client credentials) |
| `--source-client-secret` | Client secret for source authentication (Keycloak) |
| `--source-token` | Bearer token / personal access token (Zitadel PAT, Supabase `service_role` key, or a ready Keycloak token) |
| `--target-realm` | Name of the realm created in FerrisKey. See the table below for what it defaults to |
| `--dry-run` | Resolve and print the planned realm without calling the FerrisKey API |

### Name of the created realm

| Source | Name of the realm in FerrisKey |
|--------|--------------------------------|
| `config` | The `name` in the file, or `--target-realm` |
| `keycloak` | The name of the source realm, or `--target-realm` |
| `zitadel` with `--source-org` | `--target-realm`, else `--source-realm`, else `zitadel` |
| `zitadel` without `--source-org` | One realm per organization, named after it |
| `supabase` | `--target-realm`, else `--source-realm`, else `supabase` |

When several Zitadel organizations resolve, `--target-realm` is ignored and the CLI prints `note: --target-realm ignored (N realms resolved; keeping source names)` on standard error. With exactly one organization it renames the realm as usual.

### Supabase-only flags

`--source-passwords` and `--source-preserve-ids` are refused on any other source: the command stops with an error. The three `--source-include-*` flags are not checked, so on a source other than Supabase they are ignored without a message.

| Flag | Description |
|------|-------------|
| `--source-include-deleted` | Import users an operator soft-deleted. Dropped by default: their `deleted_at` is set but the row survives |
| `--source-include-anonymous` | Import anonymous sign-in sessions. Dropped by default: rows with neither an email nor a phone |
| `--source-include-unconfirmed` | Import users who never confirmed an email or a phone. Dropped by default |
| `--source-passwords <FILE>` | Carry passwords over, read from a CSV export of `auth.users`. The Auth API never serves hashes |
| `--source-preserve-ids` | Create each user with its existing Supabase id, so the `sub` of every token survives |

Each one is covered in [From Supabase](/en/cli/import/supabase).

<Callout variant="warning" title="Supabase is not in a release yet">

The latest release, 0.3.0, imports from `config`, `keycloak`, and `zitadel` only. The Supabase source, `--source-passwords`, the `--source-include-*` flags, and `--source-preserve-ids` are merged on the `main` branch of [ferriskey-cli](https://github.com/ferriskey/ferriskey-cli), but no release includes them yet. Until one does, build from the repository with `cargo install --git https://github.com/ferriskey/ferriskey-cli`.

</Callout>

```bash title="Preview a realm from a file (no FerrisKey calls)"
ferris-ctl realm import --from config --file realm.yaml --dry-run -o yaml
```

```bash title="Import a live Keycloak realm"
ferris-ctl realm import --from keycloak \
  --source-url https://keycloak.example.com \
  --source-realm acme \
  --source-client-id ferriskey-import \
  --source-client-secret "$KC_SECRET" \
  --target-realm acme
```

```bash title="Import a Supabase project, passwords and ids included"
ferris-ctl realm import --from supabase \
  --source-url https://abcdefgh.supabase.co \
  --source-token "$SUPABASE_SERVICE_ROLE_KEY" \
  --source-passwords auth_users.csv \
  --source-preserve-ids \
  --target-realm acme
```

### Dry run and report

`--dry-run` resolves the source and prints what it found without calling FerrisKey, so it needs no context and no login. It still reads the source, so the source credentials must be valid, and a `--source-passwords` file is read too. The table form shows counts: whether there are settings, and how many roles, clients, users, and passwords. With `-o json` or `-o yaml` you get the whole description as an array, with every password hash replaced by `<redacted>`.

A real import prints a report of what it created, any warnings, and the secrets of confidential clients. [Import](/en/cli/import/overview#the-import-report) describes it.

<Callout variant="info" title="Re-running an import">

Entities that already exist are reused and counted as already present; they are not updated. Realm settings and per-client settings from the source are applied again on every run. [Idempotency](/en/cli/import/overview#idempotency) lists what that means in practice.

</Callout>

The [Import](/en/cli/import/overview) section covers each source in full, including what is and isn't migrated.
