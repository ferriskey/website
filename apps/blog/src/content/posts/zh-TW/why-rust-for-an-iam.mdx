每次提到 FerrisKey 使用 Rust 編寫，大家的第一反應幾乎都是：“那它應該很快。”確實如此。我們的對比資料是公開的：空閒時只佔幾 MB 記憶體，冷啟動不到一秒；相比之下，基於 JVM 的 IAM 往往需要數百 MB 記憶體和半分鐘，才準備好響應第一個請求。

但如果全部理由只是速度，做一張營銷頁面就夠了，不需要寫這篇文章。速度是外界看到的結果，卻不是我們將關鍵安全基礎設施押在這門語言上的原因。

## IAM 承受不起的錯誤

IAM 處於攻擊者優先瞄準、又對延遲極為敏感的位置。基礎設施中的每次認證請求都依賴它。它要解析並非自己生成的權杖、無法控制的請求頭，以及不應輕易信任的客戶端發來的載荷。

從歷史上看，使用 C 或 C++ 編寫的解析器、密碼學元件和會話處理程式碼，正是行業中許多嚴重漏洞的來源。Heartbleed 並非 TLS 的設計缺陷，而是 OpenSSL 記憶體處理中發生的緩衝區越界讀取。這是一類程式錯誤，並非業務邏輯判斷有誤。

Rust 的所有權模型在編譯階段排除這類錯誤，而不只是依賴開發紀律、程式碼審查，或碰巧先發現問題的模糊測試。能夠透過編譯的 FerrisKey 二進位制程式不會包含資料競爭或釋放後使用問題。這並非某次測試的結果，而是透過 `cargo build` 的程式碼所具備的性質。

這種選擇也延伸到應用程式碼之外。TLS 棧使用 [rustls](https://github.com/rustls/rustls)，在最先接觸網路的那一層提供記憶體安全，且不依賴 C。密碼雜湊使用 `argon2`，通行金鑰與 WebAuthn 使用 `webauthn-rs`。處理攻擊者輸入的程式碼，與系統其他部分使用同一種記憶體安全語言，而非透過 FFI 邊界接入 C。

## 讓編譯器真正約束規則

基準測試中看不到的一點是：Rust 讓我們把規則從“寫在 Wiki 中，希望大家遵守”，變成“不遵守就無法編譯”。

以登入流程為例。FerrisKey 中的一次認證嘗試，只能以四種結果之一結束：

```rust title="ferriskey-domain: the login flow can only end one of four ways"
#[derive(Debug, Clone, PartialEq)]
pub enum AuthenticationStepStatus {
    Success,
    RequiresActions,
    RequiresOtpChallenge,
    Failed,
}
```

程式碼本身並不複雜。但負責將結果轉換為 HTTP 響應的處理器必須逐一匹配這些分支，遺漏任何列舉變體的 `match` 都無法透過編譯。如果明天增加第五種結果，比如通行金鑰驗證步驟，所有相關響應對映器就必須明確處理，否則構建失敗。更新不再依賴誰記得去做：遺漏分支已經不再是一條執行時路徑，而是編譯錯誤。

這就是變化所在：一條規則不再依賴資深工程師在審查時想起檢查，而是由型別系統對每位貢獻者的每次提交持續執行。

## 測試策略也隨之改變

如果無效狀態無法表示，遺漏分支無法編譯，測試就不必再反覆防守這些問題。真正需要測試的內容和測試方式都會改變。

FerrisKey 採用六邊形架構。領域層為所有與外部通訊的能力定義*埠*（trait），包括資料庫、郵件傳送器和 Webhook 分發器。其中幾個 crate 提供 `mock` 功能：

```toml title="core/Cargo.toml (trimmed)"
ferriskey-security  = { path = "../libs/ferriskey-security",  features = ["mock"] }
ferriskey-seawatch   = { path = "../libs/ferriskey-seawatch",  features = ["mock"] }
ferriskey-webhook    = { path = "../libs/ferriskey-webhook",   features = ["mock"] }
```

這裡的 mock 並不是 Mockito 或 `jest.mock()` 那樣透過反射在執行時生成的替身，而是同一 trait 的獨立實現，與其他程式碼一樣接受編譯器檢查。如果埠約定改變，mock 就必須同步更新，否則整個工作區無法構建。它不能在不被發現的情況下偏離生產環境實際呼叫的介面。

因此，測試可以將精力放在業務規則上：這次狀態轉換是否允許、這條策略是否適用、這個權杖是否已經過期，而不必在每個測試檔案中反覆確認 mock 不會崩潰、返回結構沒有錯誤。編譯器已經檢查了這一部分。

## 更快迭代，同時守住安全邊界

我們交付的每個模組，包括負責多因素認證和 WebAuthn 的 Trident、負責審計記錄的 SeaWatch，以及 Webhook 系統，都是獨立的 crate，只透過上述埠與領域核心通訊。這不是一次倉促提交就能悄悄破壞的目錄約定。模組無法繞過安全核心，觸及沒有相應埠的功能，因為編譯後的程式中不存在這樣的呼叫路徑。

這樣，我們就能更快開發，而不必以削弱安全為代價。擴充套件功能與保持信任邊界並不衝突：在我們推進功能時，編譯器也在持續約束這些邊界。

## 理論上，少一些意外

IAM 並非邊緣服務。資訊系統中的其他元件都默默依賴它保持正確。一旦出錯，受影響的不只是某個功能，而是所有下游登入和授權檢查。

對於故障時收到告警的 SRE，沒有垃圾回收器，就少了 GC 暫停在負載下造成延遲尖峰的可能。對身分域、角色和會話狀態進行窮盡匹配，意味著某些在 Java 或 Python 中仍可於執行時構造的“不可能”情況，在這裡根本無法表示成值。這當然不意味著故障不可能發生：錯誤部署、錯誤配置和對外部環境的錯誤假設仍然存在。但一整類“這到底怎麼發生的”問題，可以在釋出前被排除。至少從理論上說，未知的意外會少一些。對於如此核心的系統，這種保障值得爭取。

## 確定性為下一步帶來什麼

記憶體安全最受關注，但這種設計還有其他收益。所有權機制與沒有垃圾回收器的執行方式，也讓執行時更具確定性：沒有 GC 暫停，沒有 JIT 預熱曲線，也沒有在負載下悄悄壓縮堆的記憶體分配器。向同一個二進位制程式兩次輸入相同資料，它會沿著相同路徑執行，並表現出相同的時序特徵。這種確定性除了安全價值，也有助於控制負載下的尾延遲。

確定性同時為後續能力提供基礎。我們希望 FerrisKey 將來能走向兩個方向。

第一個方向是模擬驅動開發。FoundationDB、TigerBeetle 等系統在模擬時鐘和網路上執行整套測試，重放逐位元組相同的事件序列，同時注入連線中斷、磁碟寫入延遲和時鐘偏移等故障。這樣可以透過一個種子復現罕見錯誤，而不必花一週追蹤不穩定的 CI 失敗。要讓這種測試環境有效，程式自身不能充滿難以控制的隱藏非確定性。FerrisKey 今天還沒有這套機制，但 Rust 讓它成為可行方向，而垃圾回收時序會為模擬增加額外噪聲。

第二個方向是對最重要的不變數進行形式化證明。我們並不打算證明整個系統絕對正確，對這個規模的專案來說並不現實；目標是證明那些範圍明確、值得嚴格驗證的性質，例如已撤銷的權杖不會再次被接受，或者遺漏檢查的程式碼路徑無法跨越身分域邊界。Rust 生態中的 Kani、Creusot 和基於契約的 crate 等工具正是為此設計。型別系統已排除了許多別名和隱藏修改問題，使形式化推理更易實施。這仍在路線圖上，尚未進入生產環境，但相比於難以回答“這個指標還可能指向哪裡”的執行時，Rust 讓下一步更接近現實。

## 我們承認的代價

這些收益並非沒有成本。Rust 的學習曲線確實存在，尤其對於習慣由垃圾回收器管理記憶體的團隊。人才數量比 Java 或 Go 少，儘管正在快速增長，而且往往是主動追求這些保障的工程師。編譯時間也比動態型別語言直接執行更長。非同步生態中的某些部分仍比 JVM 或 Node 中的對應方案年輕。

對於一類軟體，我們認為這種取捨值得：它處於所有系統的關鍵路徑，是攻擊者首先瞄準的物件，而且正確性比第一天寫得快更重要。IAM 就屬於這一類。

## 最後回到大家關心的速度

所以，FerrisKey 確實很快。空閒時使用幾 MB 而非數百 MB 記憶體，冷啟動不到一秒而非三十秒。現在你知道，速度並不是最值得討論的部分。它是前述選擇帶來的可見結果：不需要等待 GC 預熱，不需要不斷擴大的堆，而編譯器會檢查程式碼所表達的約束。

速度從來不是我們選擇這條路的全部理由，它只是從外部最容易測量的結果。
