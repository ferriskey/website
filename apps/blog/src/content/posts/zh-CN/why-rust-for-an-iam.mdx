每次提到 FerrisKey 使用 Rust 编写，大家的第一反应几乎都是：“那它应该很快。”确实如此。我们的对比数据是公开的：空闲时只占几 MB 内存，冷启动不到一秒；相比之下，基于 JVM 的 IAM 往往需要数百 MB 内存和半分钟，才准备好响应第一个请求。

但如果全部理由只是速度，做一张营销页面就够了，不需要写这篇文章。速度是外界看到的结果，却不是我们将关键安全基础设施押在这门语言上的原因。

## IAM 承受不起的错误

IAM 处于攻击者优先瞄准、又对延迟极为敏感的位置。基础设施中的每次认证请求都依赖它。它要解析并非自己生成的令牌、无法控制的请求头，以及不应轻易信任的客户端发来的载荷。

从历史上看，使用 C 或 C++ 编写的解析器、密码学组件和会话处理代码，正是行业中许多严重漏洞的来源。Heartbleed 并非 TLS 的设计缺陷，而是 OpenSSL 内存处理中发生的缓冲区越界读取。这是一类程序错误，并非业务逻辑判断有误。

Rust 的所有权模型在编译阶段排除这类错误，而不只是依赖开发纪律、代码审查，或碰巧先发现问题的模糊测试。能够通过编译的 FerrisKey 二进制程序不会包含数据竞争或释放后使用问题。这并非某次测试的结果，而是通过 `cargo build` 的代码所具备的性质。

这种选择也延伸到应用代码之外。TLS 栈使用 [rustls](https://github.com/rustls/rustls)，在最先接触网络的那一层提供内存安全，且不依赖 C。密码哈希使用 `argon2`，通行密钥与 WebAuthn 使用 `webauthn-rs`。处理攻击者输入的代码，与系统其他部分使用同一种内存安全语言，而非通过 FFI 边界接入 C。

## 让编译器真正约束规则

基准测试中看不到的一点是：Rust 让我们把规则从“写在 Wiki 中，希望大家遵守”，变成“不遵守就无法编译”。

以登录流程为例。FerrisKey 中的一次认证尝试，只能以四种结果之一结束：

```rust title="ferriskey-domain: the login flow can only end one of four ways"
#[derive(Debug, Clone, PartialEq)]
pub enum AuthenticationStepStatus {
    Success,
    RequiresActions,
    RequiresOtpChallenge,
    Failed,
}
```

代码本身并不复杂。但负责将结果转换为 HTTP 响应的处理器必须逐一匹配这些分支，遗漏任何枚举变体的 `match` 都无法通过编译。如果明天增加第五种结果，比如通行密钥验证步骤，所有相关响应映射器就必须明确处理，否则构建失败。更新不再依赖谁记得去做：遗漏分支已经不再是一条运行时路径，而是编译错误。

这就是变化所在：一条规则不再依赖资深工程师在审查时想起检查，而是由类型系统对每位贡献者的每次提交持续执行。

## 测试策略也随之改变

如果无效状态无法表示，遗漏分支无法编译，测试就不必再反复防守这些问题。真正需要测试的内容和测试方式都会改变。

FerrisKey 采用六边形架构。领域层为所有与外部通信的能力定义*端口*（trait），包括数据库、邮件发送器和 Webhook 分发器。其中几个 crate 提供 `mock` 功能：

```toml title="core/Cargo.toml (trimmed)"
ferriskey-security  = { path = "../libs/ferriskey-security",  features = ["mock"] }
ferriskey-seawatch   = { path = "../libs/ferriskey-seawatch",  features = ["mock"] }
ferriskey-webhook    = { path = "../libs/ferriskey-webhook",   features = ["mock"] }
```

这里的 mock 并不是 Mockito 或 `jest.mock()` 那样通过反射在运行时生成的替身，而是同一 trait 的独立实现，与其他代码一样接受编译器检查。如果端口约定改变，mock 就必须同步更新，否则整个工作区无法构建。它不能在不被发现的情况下偏离生产环境实际调用的接口。

因此，测试可以将精力放在业务规则上：这次状态转换是否允许、这条策略是否适用、这个令牌是否已经过期，而不必在每个测试文件中反复确认 mock 不会崩溃、返回结构没有错误。编译器已经检查了这一部分。

## 更快迭代，同时守住安全边界

我们交付的每个模块，包括负责多因素认证和 WebAuthn 的 Trident、负责审计记录的 SeaWatch，以及 Webhook 系统，都是独立的 crate，只通过上述端口与领域核心通信。这不是一次仓促提交就能悄悄破坏的目录约定。模块无法绕过安全核心，触及没有相应端口的功能，因为编译后的程序中不存在这样的调用路径。

这样，我们就能更快开发，而不必以削弱安全为代价。扩展功能与保持信任边界并不冲突：在我们推进功能时，编译器也在持续约束这些边界。

## 理论上，少一些意外

IAM 并非边缘服务。信息系统中的其他组件都默默依赖它保持正确。一旦出错，受影响的不只是某个功能，而是所有下游登录和授权检查。

对于故障时收到告警的 SRE，没有垃圾回收器，就少了 GC 暂停在负载下造成延迟尖峰的可能。对身份域、角色和会话状态进行穷尽匹配，意味着某些在 Java 或 Python 中仍可于运行时构造的“不可能”情况，在这里根本无法表示成值。这当然不意味着故障不可能发生：错误部署、错误配置和对外部环境的错误假设仍然存在。但一整类“这到底怎么发生的”问题，可以在发布前被排除。至少从理论上说，未知的意外会少一些。对于如此核心的系统，这种保障值得争取。

## 确定性为下一步带来什么

内存安全最受关注，但这种设计还有其他收益。所有权机制与没有垃圾回收器的运行方式，也让运行时更具确定性：没有 GC 暂停，没有 JIT 预热曲线，也没有在负载下悄悄压缩堆的内存分配器。向同一个二进制程序两次输入相同数据，它会沿着相同路径执行，并表现出相同的时序特征。这种确定性除了安全价值，也有助于控制负载下的尾延迟。

确定性同时为后续能力提供基础。我们希望 FerrisKey 将来能走向两个方向。

第一个方向是模拟驱动开发。FoundationDB、TigerBeetle 等系统在模拟时钟和网络上运行整套测试，重放逐字节相同的事件序列，同时注入连接中断、磁盘写入延迟和时钟偏移等故障。这样可以通过一个种子复现罕见错误，而不必花一周追踪不稳定的 CI 失败。要让这种测试环境有效，程序自身不能充满难以控制的隐藏非确定性。FerrisKey 今天还没有这套机制，但 Rust 让它成为可行方向，而垃圾回收时序会为模拟增加额外噪声。

第二个方向是对最重要的不变量进行形式化证明。我们并不打算证明整个系统绝对正确，对这个规模的项目来说并不现实；目标是证明那些范围明确、值得严格验证的性质，例如已撤销的令牌不会再次被接受，或者遗漏检查的代码路径无法跨越身份域边界。Rust 生态中的 Kani、Creusot 和基于契约的 crate 等工具正是为此设计。类型系统已排除了许多别名和隐藏修改问题，使形式化推理更易实施。这仍在路线图上，尚未进入生产环境，但相比于难以回答“这个指针还可能指向哪里”的运行时，Rust 让下一步更接近现实。

## 我们承认的代价

这些收益并非没有成本。Rust 的学习曲线确实存在，尤其对于习惯由垃圾回收器管理内存的团队。人才数量比 Java 或 Go 少，尽管正在快速增长，而且往往是主动追求这些保障的工程师。编译时间也比动态类型语言直接运行更长。异步生态中的某些部分仍比 JVM 或 Node 中的对应方案年轻。

对于一类软件，我们认为这种取舍值得：它处于所有系统的关键路径，是攻击者首先瞄准的对象，而且正确性比第一天写得快更重要。IAM 就属于这一类。

## 最后回到大家关心的速度

所以，FerrisKey 确实很快。空闲时使用几 MB 而非数百 MB 内存，冷启动不到一秒而非三十秒。现在你知道，速度并不是最值得讨论的部分。它是前述选择带来的可见结果：不需要等待 GC 预热，不需要不断扩大的堆，而编译器会检查代码所表达的约束。

速度从来不是我们选择这条路的全部理由，它只是从外部最容易测量的结果。
